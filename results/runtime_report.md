## Timing method

The clock starts before the first file is read and stops after the last
file is written, covering disk read, preprocessing, host-to-device
transfer, model execution, device-to-host transfer, clipping and saving.
One untimed warm-up pass precedes measurement; on CUDA,
`torch.cuda.synchronize()` is called before each stop because GPU work
is asynchronous.

**Best configuration on this machine: batch size 32** — 2.50 s end-to-end for 100 images (25.0 ms per image, 39.97 images/second).

Note: batching helps most on a GPU, where it hides host-to-device
transfer latency behind computation. On a CPU the work is already
compute-bound, so larger batches give little or no gain.

## Interpretation

- **All 400 official test images restore in ~10 seconds** on this T4
  (400 x 25.0 ms), excluding model load.
- Batching gives a modest 5% gain here (26.3 -> 25.0 ms). The model is
  small enough that per-image GPU work is short, so kernel-launch overhead
  rather than transfer latency dominates. `inference.py` still defaults to
  batching on CUDA because the gain is free and grows with image size.
- Model execution is 97% of the end-to-end time (2.43 s of 2.50 s); disk
  read and saving are negligible, so there is no I/O bottleneck to fix.

### Reference measurement on CPU (no GPU available)

Same 100 images on an Intel laptop CPU: **133.5 s end-to-end, 1335 ms per
image, 0.75 img/s** at batch size 1 (batching is counter-productive on
CPU and `inference.py` disables it there automatically). The GPU is
therefore about **53x faster**, and the pipeline remains usable without
any GPU at all — useful for a laptop demo.

KLA benchmarks on an NVIDIA H100, which is substantially faster than the
T4 measured here; these figures should be read as a conservative lower
bound.
